## Partner dashboard pre-authentication ingress control

The partner dashboard authentication middleware looks up a partner-specific JWT secret in PostgreSQL before token verification. Its routes therefore require two distinct controls: a shared IP-keyed ingress budget before `partnerAuth`, followed by the authenticated-principal budget after successful verification. The ingress limiter uses Express `req.ip`; before rollout, verify the deployed `trust proxy` hop configuration against the actual Render/network topology, prove client-supplied forwarding headers cannot spoof the trusted address, and test IPv4/IPv6 normalization and shared quotas across instances. Do not replace this with an untrusted raw `X-Forwarded-For` header. Confirm database capacity and fail-closed behavior under rate-limit-store latency/outage. The new ingress control is draft code only until exact-head CI, staging tests, and independent review pass.

## Bounded maintenance
`runRateLimitMaintenance(pool, { batchSize, maxBatches })` performs bounded batches of expired-row cleanup, stops early on a short batch, and reports budget exhaustion. The default invocation permits five batches of 1,000 rows. Errors propagate to the caller; scheduling, authorized worker identity, DB timeouts, monitoring and grants remain external release gates. No scheduler or database mutation has been enabled by this change.
