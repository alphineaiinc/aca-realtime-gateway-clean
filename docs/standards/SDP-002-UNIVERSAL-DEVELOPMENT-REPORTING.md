# Alphine AI — Universal Development and Reporting Standard (SDP-002)

Version 1.0 | Owner approved 2026-11-24 subject to compatibility verification | Working standard on draft PR #126; not merged or enforced branch policy.

## Authority and compatibility
Applies to all current and future Alphine AI projects. Companion to [SDP-001 v1.1](../PHASE2_STANDARD_DEVELOPMENT_PROCEDURE.md), reviewed at blob 9857107a88fbc01b991c054dc95bd61b3b472578. SDP-001 gates 0–5, per-item record, fail-closed rules, independent review, exact-head validation, stop conditions and specific owner authorization remain mandatory. In conflict apply the stricter restriction and escalate. This standard grants no operational permission.

## Mandatory execution
Resume authoritative repository/tracker checkpoint, exact branch/head, baseline, dependencies and approvals. Proceed/Continue/Next/Go ahead means execute the next substantial coherent authorized batch, not merely plan it. Prioritize existing scope, actual source corrections, integration and executable acceptance. Finish small residual work and continue other safe independent tasks in the active session. Do not repeat unchanged checks unnecessarily; revalidate changed heads. Escalate after two unsuccessful focused correction attempts or immediately on risky uncertainty. Never imply background execution. Preserve coherent reviewable drafts, no overwriting concurrent changes, no secrets or customer data in evidence.

## Permanent task accounting
Keep approved IDs, exit criteria, dependencies, evidence and denominator fixed. ACA #129 retains 48; Development Automation #118 retains 44. Complete only when existing criteria pass at the stated scope. Partial and pending remain outstanding; blocked is an additional flag, not double counted. Preserve SDP-001 development-ready/release-ready/complete distinctions and original project status mappings. Report implementation evidence separately from formal acceptance, independent review, operational readiness and owner release. Percentage = completed IDs / approved denominator x 100; label implementation coverage separately and do not imply effort-weighted completion. New defects map to existing IDs; new requirements or baseline revisions need owner approval, rationale and impact. No silent scope expansion.

## Mandatory substantive update format
1. Project, batch, SOP versions, scope and restrictions.
2. Executive result: actual work performed, not plans.
3. Completed/advanced IDs and evidence (SHA, run/job, environment, criteria PASS/FAIL/BLOCKED/NOT TESTED).
4. Overall dashboard: counts, denominator, percentage and visual progress bars; formal acceptance separately.
5. Story/phase-level progress bars and counts.
6. Complete numbered permanent checklist with status and blockers.
7. Daily opening/current/delta table and actual commits, defects, tests, CI, acceptance and spend.
8. Remaining coordinated roadmap mapping every outstanding ID through release.
9. Concrete blockers, limitations, assumptions and owner decisions.
10. Compliance: spend, production/staging changes, merges, credentials, providers, agents, fixtures, rollback/restoration, tracker and evidence links.
11. Functional clickable Proceed control carrying exact next batch/checkpoint, restrictions and deliverables; if unsupported provide copyable continuation prompt. Approval controls must explicitly identify protected action and not bundle unrelated permissions. No continuation control if no eligible action; explain blocker.
Short informational questions may use compact prose.

## Daily accountability and commands
America/Toronto calendar day, fixed verified opening checkpoint across chats; report unknown when unavailable. Goodnight: consolidated daily summary, opening/current accepted and implementation counts, percentage-point changes, IDs advanced, actual commits/tests/CI, phase progress, blockers, decisions, CAD spend, remaining effort forecast (label estimates), next batch. Good morning: recover checkpoint and resume authorized work. Status: master baseline. Never invent deltas.

## Evidence and authorization
Record exact SHA and scope, actual test/run/job/scanner results, environment, timestamp, reviewer and limitations. Distinguish source review, mocks, integration, staging, actual providers and default-branch evidence. Green CI is not independent clearance; isolated CodeQL is not live alert closure. Pending/missing is not PASS. Preserve SDP-001 alert-level disposition and acceptance records. Consolidate related owner decisions with scope, environment, cost ceiling, risk and expected deliverables. No merge, staging/production deployment, activation, migration, signing, dispatch, credential creation/rotation, security settings change, destructive operation or extra cost without applicable specific authorization. Generic Proceed never waives gates. Default CAD $0 unless explicitly approved otherwise.

## Continuity and release
Repository and master tracker are authoritative; memory supplementary. Record checkpoint and update linked tracker without overwriting concurrent edits. Do not restart completed work or extend scope unnecessarily. Transition from implementation to operational acceptance when appropriate. Release requires all applicable existing exit criteria, independent security, operational/provider acceptance, rollback readiness and explicit owner approval. No self-approval. Version changes require owner approval and recorded rationale.

## Reusable project instruction
Follow SDP-001 v1.1 and SDP-002 v1.0 at the approved repository revision. On Proceed execute large coordinated authorized batches, recover checkpoint, preserve permanent IDs and denominator, validate exact-head evidence, update tracker and daily accountability, and use all eleven reporting sections above. Preserve all existing security and spending restrictions. Always provide functional Proceed or explicit approval control when appropriate, with copyable fallback. Goodnight/Good morning/Status follow the daily command rules. Project-specific scope and approvals remain separate. Never fabricate work or progress.
